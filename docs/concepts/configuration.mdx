Configuration is realm-scoped. The active `realm_id` determines which raw
config document is read and written.

## Realm-scoped config

An ordinary non-global realm keeps these files in its resolved realm directory:

- `config.toml` (user settings)
- `config_state.json` (generation counter for CAS)
- `realm_manifest.json` (pinned backend + metadata)

The reserved `global` config document and its config-generation sidecar are the
exception: they are home-rooted at `~/.rkat/config.toml` and
`~/.rkat/config_state.json`. Global config can be inherited, but a global
realm's runtime state is never inherited.

For CLI commands, the normal non-global location is project-local:

```text
<project-root>/.rkat/realms/<realm>/
```

Here `project-root` is the nearest ancestor containing `.rkat`. Outside an
existing project, it falls back to the exact invocation context. The invocation
context itself is never walked up for workspace realm identity or MCP trust
discovery, so identity and the local storage candidate are intentionally
separate facts. An explicit `--state-root` bypasses candidate probing.

For daemon/API surfaces that do not receive a `--state-root`, the default state
root is the platform data directory:

- macOS: `~/Library/Application Support/meerkat/realms/<realm>/`
- Linux: `~/.local/share/meerkat/realms/<realm>/`
- Windows: `%APPDATA%\meerkat\realms\<realm>\`

Use [realms](/concepts/realms) to choose whether state is shared or isolated.

## Realm config inheritance

A realm config doc may declare a `parent`, and resolution walks a single chain
`head -> parent -> ... -> global`. A terminal non-global realm appends
`global` when a global section is configured. The chain can also end before
`global` when no global config has been materialized.

```toml
[realm.team]
parent = "org"
```

- **Config inherits** along the chain: models, MCP servers, hooks, skills,
  limits, and auth bindings are composed parent-first with child-wins.
- **State never inherits**: sessions, session stores, event stores, and the
  `.rkat/` projection stay realm-local to the consuming (head) realm.

The `global` realm's config document is **home-rooted** at `~/.rkat/config.toml`
(a single well-known location, not a per-workspace file), which is why a single
interactive `rkat auth login` is inherited by every workspace realm via the
chain tail. See
[Realm inheritance](/concepts/realm-inheritance) for the full model, including
credential read-inherit / write-strict-owner and the add/override-but-not-remove
rules for MCP servers and hooks.

## Effective precedence

For an agent build in a given realm, effective precedence is:

1. Built-in defaults
2. A configured `global` root and explicit ancestors, folded root-first
3. The head realm's own `config.toml`
4. Per-request runtime parameters (for example model, system prompt, or tool
   toggles on create/resume calls)

The agent build path on every surface (CLI, REST, RPC, MCP server) composes this
effective config over the head realm, so model/MCP/hook/skill/limit inheritance
applies on every build, not just the auth path. `config get` / `config set`
operate on the **raw head doc** (a read/write split): an inherited entry is
read through composition and never copied into the child's own doc. This does
not make a `config get` then `config set` round trip safe in a child realm:
`config get` returns the head doc as a typed config with every default filled
in, and `config set` writes all of it back as the child's own values. Use
`config patch` for partial edits.

This shared configuration path does not install native permission owners.
Native governance requires explicit trusted-host composition. The stock hosts
select OS process confinement from the `[confinement]` section and their
`--confinement` flags (see [OS process confinement](#os-process-confinement));
a Rust embedding installs it on its own factory. See
[authorization integration](/guides/authorization-integration) for the supported
profiles and [native governed embedding](/rust/native-authorization) for setup.

Environment variables still matter, but they are primarily part of **runtime credential resolution**, not a general config layer that mutates the loaded realm config. In practice:

- realm config remains the canonical persisted settings surface
- provider credentials can still come from `RKAT_*` or provider-native env vars at resolve time
- bindings and auth profiles decide how those credentials are used at runtime

## Config APIs and CAS

RPC, REST, and MCP all expose the same config envelope:

- `config`
- `generation`
- `realm_id`
- `instance_id`
- `backend`

Some surfaces also expose `resolved_paths` in diagnostic/admin contexts. Treat that field as optional rather than universal across all public config envelopes.

Writes support optimistic concurrency:

- `config/set` and `config/patch` accept optional `expected_generation`
- stale writes return generation conflict

This gives deterministic behavior when multiple clients or processes update config concurrently.

## Merge semantics

Meerkat uses three update models:

1. Layered config loading (`defaults -> file -> runtime`) uses **section-specific merge rules**:
  - optional settings such as `max_tokens` override when present; many non-optional scalars override only when nondefault
  - `shell`, `store`, `comms`, `compaction`, and `rest`: a nondefault incoming section replaces the whole section, including its omitted fields' defaults
  - hook entries append; hook scalar settings override only when nondefault
2. Realm-chain composition reuses those rules, folding each realm doc parent-first:
  - per-provider model defaults: union, child-wins per provider (a child overrides its anthropic default while inheriting the parent's openai default)
  - MCP servers: map-key union, child-wins per name (add or override, never remove)
  - hook entries and skill sources: append parent-first (child cannot remove inherited entries); hook scalars retain the nondefault-value rule
  - limits: per-field optional child-wins (a child can tighten `max_sessions` while inheriting other caps)
  - `shell`, `store`, `comms`, `compaction`, and `rest`: retain nondefault whole-section replacement, not per-field inheritance
  - filesystem-backed docs additionally use raw TOML presence for `tools`, `retry`, and `skills` overrides, so explicitly setting a supported field to its default can override a parent; this is not a universal rule for all scalar fields or non-filesystem sources
  - `model_fallback`: a nondefault table replaces the inherited table as a whole; an empty/default-valued table inherits, while `enabled = false` explicitly replaces and disables
  - `governance`: a present section, even an empty one, replaces the inherited one as a whole; a document without it inherits it
  - `confinement`: per launch kind, a requirement only holds or is added; a less trusted document cannot replace or remove it (see [composition](#composition))
  - the binding/backend/auth maps are **not** merged across realms: each realm's binding resolves its `backend_profile` / `auth_profile` only within its own section (the owning realm)
3. Runtime patch APIs (`config/patch`, `PATCH /config`) use **RFC 7396 JSON merge-patch** semantics.

Use `config/set` when replacing the whole config intentionally, and `config/patch` for surgical updates.

<Warning>
`config/set` (and `rkat config set`, including any partial `--toml`, `--json`
or FILE payload) writes a full typed config: every key the request leaves out
is written with its default. The MCP server's `meerkat_config` set refuses a
partial payload, but a complete one has the same effect. In a child realm
each of those keys becomes the child's own override, so the realm stops
inheriting it, and capabilities the parent disabled whose defaults are on
(`tools.schedule_enabled`, provider web search, Gemini Google search,
`skills.enabled`) are enabled again. A `config get` then `config set` round
trip has the same effect. `config/patch` writes only the keys it names and
keeps the rest of the document as written; a `null` value removes a key so
the realm inherits it again.
</Warning>

### Presence-based override (Option fields)

`Config.max_tokens` and `agent.max_tokens_per_turn` are optional. `None` means
"inherit / use the template default" and is resolved at point-of-use
(`resolved_max_tokens` / `resolved_max_tokens_per_turn`). Merge for these fields is
**presence-based** (an explicit value wins, regardless of whether it equals the
default), so a child realm can override a non-default parent value back **down to
the default** - something a `!= default` heuristic could not express.

## Agent turn limits

Set `agent.max_turns` to bound the model-loop iterations in one agent run:

```toml
[agent]
max_turns = 700
```

An omitted value inherits from the parent realm. If the entire chain omits
it, agent construction uses the default of `100`. An explicit value always
overrides the parent, including `100` and `0`.

`max_turns = 0` terminates immediately with the `TurnLimitReached` cause,
before the first model request; zero does not mean unlimited. The counter
resets for each run, so this is not a limit on the number of user messages
in a session. Direct Rust callers can set the same limit with
`AgentBuilder::max_turns(u32)`.

## CLI behavior

CLI config commands operate on the selected realm:

```bash
rkat --realm team-alpha config get --format json
rkat --realm team-alpha config get --format json --with-generation
rkat --realm team-alpha config patch --json '{"agent":{"model":"gpt-5.5"}}' --expected-generation 4
```

Without `--realm`, CLI derives a stable workspace realm (`ws-...`) from the
current directory, or from `--context-root` when supplied.

## What About `~/.rkat/config.toml` And `.rkat/config.toml`?

`~/.rkat/config.toml` is the home-rooted config document for the reserved
`global` realm. Interactive `rkat auth login` writes the `[realm.global]` binding
section here; once configured, it is the implicit chain tail for workspace
realms.

The project-root `.rkat/config.toml` still exists for `rkat init`, legacy
single-file loading, and explicitly layered hook discovery. Do not confuse it
with the active non-global realm document at
`<state-root>/<realm>/config.toml`, which is the canonical raw head store used
by CLI/RPC/REST/MCP runtime composition.

## Backend and storage settings

Session backend is pinned per realm in `realm_manifest.json` (`sqlite`, `jsonl`, or `memory`).
`--realm-backend` only matters on first creation of a realm.

`[storage] hosting` declares how many processes may serve the realm at once:

```toml
[storage]
hosting = "multiprocess"   # default: "single_process"
```

It is layered like every realm option (a child realm's explicit value, including
`single_process`, wins). With `multiprocess`, every surface refuses to start when the
realm's stores cannot provide trusted cross-process hosting. See
[Realms: multi-process hosting](/concepts/realms#multi-process-hosting).

## Compaction settings

Compaction runtime policy is configurable in realm config:

```toml
[compaction]
auto_compact_threshold = 100000
# max_request_bytes = 9000000 # optional operator override
recent_turn_budget = 4
max_summary_tokens = 4096
min_turns_between_compactions = 3
history_retained_rewrites = 4
```

When `session-compaction` is enabled, `AgentFactory` maps these values into
the runtime `CompactionConfig`. If `auto_compact_threshold` is omitted,
cataloged models scale the token trigger to 80 percent of the smaller of their
context window and separate input ceiling, when one is declared. For
`gpt-6-astra`, the 922,000-token input ceiling gives a 737,600-token default
trigger; its shared input-plus-output context window remains 1,050,000 tokens.
Built-in provider clients also attach the current provider's approximate
request-byte cap to each lowered request; the byte trigger fires at 80 percent
of that cap. `max_request_bytes` is an optional operator override, especially
useful for a self-hosted gateway whose limit is not in the catalog.

Compaction is checked against both token and serialized-request pressure.
Inline media can exhaust a provider byte limit long before the token estimate
reaches its threshold.

`history_retained_rewrites` bounds the transcript history a session document
keeps. Each compaction is a recorded transcript rewrite, and the session's
rewrite graph holds the history needed to reconstruct earlier revisions.
After each compaction, only the most recent `history_retained_rewrites`
rewrites keep that history. Older rewrites keep their commit records and
digests, and their message bodies are dropped. Without the bound, a session
document kept every message it ever produced, however often it compacted. A
fork, rewind, restore or revision read that targets a revision older than the
window fails with a typed error naming the oldest retained revision. The
SQLite store applies the same bound to its rows: each compaction's write
deletes the stored history below the window in the same transaction.

## Retry and stream watchdog settings

LLM retry policy (`RetryPolicy`) is configurable in realm config:

```toml
[retry]
max_retries = 3
initial_delay = "500ms"
max_delay = "30s"
multiplier = 2.0
call_timeout = "45s"                 # omit to inherit the model-profile default
stream_inactivity_timeout = "300s"   # omit to inherit the model's window; "disabled" turns it off
```

`call_timeout` is a tri-state override for the hard per-LLM-call deadline:
omitted inherits the profile-derived default, `"disabled"` turns it off, and
a duration sets it explicitly.

`stream_inactivity_timeout` is the per-provider-stream inactivity
watchdog. It is **on by default** with a 300-second window: an LLM call
whose stream reports no events for the window is aborted with the retryable
`StreamStalled` failure and flows through normal retry handling. Each received stream
event re-arms the window, so long-but-alive responses are unaffected. Set
`stream_inactivity_timeout = "disabled"` to opt out, or a duration
(`"120s"`) for an explicit window for every model. Like `call_timeout`, an
omitted value inherits from the model profile: a model whose provider
documents responses that can stay silent for minutes has its own catalog
window (`gemini-4-argon`: 900 s, `gpt-5.5-pro`: 7200 s), a self-hosted model
can declare one with `stream_inactivity_timeout_secs` (at least 60 seconds;
config validation refuses a shorter one), and every other model uses the
built-in 300 s. The window is resolved for each LLM call, so a model change or
fallback uses the new model's window. The watchdog covers all built-in
provider clients; a custom `AgentLlmClient` that does not report stream
liveness fails open (no watchdog; only the hard call timeout applies).

An explicit `stream_inactivity_timeout` must be greater than zero: config
validation refuses `"0s"`, which would stall every call; use `"disabled"` to
turn the watchdog off. Keep an explicit window at 60 seconds or more. The
OpenAI-compatible client waits up to 30 seconds after the model's final event
for its usage trailer, and the watchdog keeps running through that wait, so a
shorter window can abort and retry a stream whose answer already arrived.

Unknown provider failures also enter the machine-authorized bounded retry path.
Explicit terminal classes such as invalid requests, authentication failures,
exhausted quota or credit (OpenAI `insufficient_quota`, Anthropic spend caps,
Gemini daily quota), missing models, content filtering, context overflow, and
oversized requests remain non-retryable. With the default `max_retries = 3`,
a persistently unknown failure can make four provider attempts before
returning `retry_exhausted`.

## Turn and agent-lifetime bounds

The timeouts above bound one *segment* of a turn: a single LLM call, a single
provider stream, a single tool call. Their **sum** is a separate fact with a
separate owner:

```toml
[limits]
budget = 200000              # max tokens, agent lifetime
max_tool_calls = 500         # max tool calls, agent lifetime
max_duration = "4h"          # wall-clock ceiling for the AGENT'S LIFETIME
max_turn_duration = "30m"    # aggregate wall-clock ceiling for ONE TURN
```

`max_turn_duration` is the aggregate bound. Its clock is re-armed at every run
entry, so it measures one turn end-to-end no matter how many LLM calls,
retries, and tool batches that turn contains. Exceeding it takes the existing
time terminal, `TurnTerminalOutcome::TimeBudgetExceeded`, which surfaces as
`AgentError::TerminalFailure { outcome: TimeBudgetExceeded, .. }`. Note the
asymmetry with the other budget dimensions, which is deliberate: an exhausted
token or tool-call budget is an orderly stop that still answers the caller,
while an exhausted deadline is a hard failure. A turn past its deadline can no
longer promise what it did or when it will answer, so it fails closed rather
than reporting a warning and continuing.

`max_duration` is **not** a per-turn deadline. Its clock starts when the
session's agent is built and is never re-armed, so it measures the agent's
whole lifetime including idle time between turns. Setting it low to bound a
turn will terminalize a later turn that did no work.

Both are unset by default: turns are unbounded in aggregate unless a
deployment declares a ceiling. The bound is enforced at segment boundaries, so
it never tears down a tool call that is already running; the effective ceiling
is `max_turn_duration` plus the longest segment already in flight (at most one
per-tool-call timeout, since calls in a batch run their clocks together).

Before a limit stops a run, the agent warns once: when tokens, tool calls, or
a time horizon reach `[agent] budget_warning_threshold` of their limit (`0.8`
by default), it emits a `budget_warning` event whose `percent` is the fraction
used. The per-turn horizon warns again each turn. The value takes effect when
it is greater than 0 and at most 1; `1.0` keeps only the `budget_warning`
emitted when a limit is reached. A config with a value outside that range
still loads, with a warning, and keeps the inherited threshold (the default if
no parent realm sets one).

```toml
[agent]
budget_warning_threshold = 0.8
```

`limits.max_sessions` controls active-session admission; persisted history
does not consume the limit. RPC, REST, and MCP snapshot this value when their
session service builds its admission semaphore. Changing config does not resize
an already-running service; rebuild or restart it to apply the new limit.

## HTML Presentation Defaults

HTML rendering is surface-requested. The `Config` schema accepts a default
template and optional custom templates:

```toml
[presentation.html]
default_template = "polished"

[presentation.html.templates.incident]
path = "./templates/incident.html"
```

This is accepted configuration syntax, but the ordinary CLI realm-composition
path currently does not propagate `presentation`. On that path, neither a
configured default nor these named custom templates reaches the HTML resolver.
This limitation does not describe direct Rust consumers of a parsed `Config`.

HTML output itself still works. Select the builtin explicitly or read a custom
template file directly:

```bash
rkat run --html --html-template polished "Explain this design"
rkat run --html --html-template-file ./templates/incident.html "Summarize this incident"
```

Configuration does not turn ordinary runs into HTML; request `--html`,
`--output html`, or `--browser`.

## Model fallback settings

Model fallback is disabled by default. Enabling it requires a non-empty,
explicit ordered chain. There is no implicit catalog fallback:

```toml
[model_fallback]
enabled = true

[model_fallback.policy]
cross_provider = true
min_context_headroom = 0.10
require_tool_parity = true
trigger_after_attempts = 3
triggers = ["capacity", "provider_unavailable"]

[[model_fallback.chain]]
model = "claude-opus-4-8"
provider = "anthropic"

[[model_fallback.chain]]
model = "gpt-5.5"
provider = "openai"
auth_binding = { realm = "global", binding = "openai_oauth" }
```

A fallback target is identified by model, provider, self-hosted server, and
`auth_binding`. The same model/provider with a different credential binding is
a valid target. Cross-provider candidates are skipped before credential lookup
unless `cross_provider = true` (default false).

Use `enabled = false` to disable an inherited policy. A nondefault child
fallback table replaces the inherited table as a whole. Omitted tables and
empty/default-valued tables inherit; explicit `enabled = false` is nondefault
and therefore replaces the parent.
A chain alone never enables fallback.

Writes and loads treat two legacy shapes differently:

- **Writes are strict.** A config set or patch (CLI, REST, RPC, MCP, SDK stores)
  that introduces `enabled = true` with an empty chain on a document that did
  not already have that shape is rejected, and so is any unknown fallback key,
  including the removed `use_catalog_default_chain` and unsupported
  scope/expiry/revert options. A patch that restates `enabled = true` with an
  empty chain on a document that already has it is not rejected: it is
  normalized like a load (see below) and reports the warning.
- **Loads of persisted documents are lenient** for the two shapes that config
  files written by rkat 0.8.36 and earlier can contain. The document still
  loads, the legacy setting is ignored, and the surface reports a typed warning
  (`ConfigWarning`) naming the file. `rkat` prints it once per file on stderr
  without changing the exit status; servers log it once per file.

| Persisted shape | Loaded as | Warning |
| --- | --- | --- |
| `[model_fallback] enabled = true` with no `[[model_fallback.chain]]` (the template default through 0.8.36, then meaning the catalog default chain) | ignored: no fallback policy, so it inherits the parent's explicit policy, off if none | `LegacyModelFallbackDefault` |
| `use_catalog_default_chain` under `[model_fallback]` (documented through 0.8.36) | `= true`: the whole table is ignored (as in 0.8.36, where it replaced the table), so it inherits the parent's explicit policy, off if none. `= false`: only the key is ignored and the table's other settings stand | `LegacyModelFallbackCatalogChain` |

A legacy table loads as if it were absent. That matches 0.8.36, where a child
realm's `enabled = true` table with no chain equalled the default and inherited
its parent's policy, so a reviewed chain on a parent realm keeps applying to
children written by 0.8.36. Fallback only ever uses explicit
`[[model_fallback.chain]]` entries; the removed catalog chain is never used. A
load never rewrites the file. The next write to that document drops the legacy
setting (the `enabled` key of the first shape, and `use_catalog_default_chain`).
A patch merges onto the document as persisted, so a patch that adds a
`[[model_fallback.chain]]` target to an `enabled = true` document keeps
`enabled = true` and turns fallback on; any other patch drops the legacy
setting and reports the warning. To silence a warning, delete the
`[model_fallback]` table, or add an explicit `[[model_fallback.chain]]`.

Only realms on the resolved inheritance chain are reported when a config is
composed, so `~/.rkat/config.toml` is reported there only when it is on that
chain. Operations on the global document itself report it too: `rkat auth
login`, `rkat config get --realm global`, and the `rkat` credential setup that
rewrites it.

Explicit `brain_swap` requests are independent of automatic fallback settings.
Target discovery uses the effective model catalog, configured realm routes,
account affinity, and installed provider runtimes; it does not resolve foreign
credentials or prebuild foreign clients. The active route remains eligible,
including an environment-backed active route, but an unconfigured foreign
environment-only route is not advertised. Credential and client admission still
occur through the canonical runtime realization before the next turn; a staged
request is not a committed switch.
Separately enabled image generation may resolve its own provider credentials;
disabling automatic model fallback does not disable image features. An explicit
image-generation disable skips that feature's automatic executor discovery.

Mob definitions also accept `[runtime.model_fallback]` and
`[profiles.<name>.model_fallback]`. A present profile table wins over mob runtime,
which wins over host config; explicit false is preserved through materialization
and portable profile revival.
Realm-profile references cannot add a fallback override beside `realm_profile`;
put it on the referenced profile or in the mob runtime table instead.

Fallback activation is still runtime-governed: the generated recovery
authority must classify the LLM failure as recoverable, and the core run loop
must decide the retry is pre-stream safe. Defaults consider capacity and provider
unavailability only after three failed attempts. Transport and empty-output
failures never migrate by default; ordinary bounded retries remain separate.
Migration is suppressed after visible text or reasoning.

Admission uses the actual hydrated, compacted request, output reserve, target
context limits, required tools/modalities, structured output, and credential
authority. Unsafe candidates produce typed `model_fallback_skipped` events,
even if every candidate is rejected. Staging is not commitment; only
`model_fallback_committed` confirms the canonical sticky route changed.

New fallback commits persist target-bound provenance in the same canonical
control transaction. An unsafe fallback-origin resume requires explicit model
reconfiguration; explicit identity overrides obsolete that provenance. There is
no automatic restoration or migration of pre-0.8.37 sticky routes: historical
notice text and brain-swap history are not fallback authority. Scoped overlays,
expiry, timed reversion, and doctor/migration redesign remain unsupported.

## Governance settings

A stock governed realm can require review above R1 for exact operation
targets. Each rule names one target, by the name its owner registers it under
(never a model-facing display name), and the tier it requires:

```toml
[[governance.review.rules]]
target = { kind = "mcp_operation", server = "mail", operation = "send" }
tier = "r3"
consent_assurance = "person_authenticated"

[[governance.review.rules]]
target = { kind = "mcp_server", server = "calendar" }
tier = "r2"

[governance.review.reviewer]
identity = { model = "claude-sonnet-5-5", provider = "anthropic" }
max_output_tokens = 1024
```

- `target`: `mcp_server` (every operation of one configured MCP server),
  `mcp_operation` (one raw operation of one server) or
  `tool_bundle_operation` (one operation of a registered tool bundle). Each
  target appears once.
- `tier`: `r2` (the configured reviewer model reviews the exact operation
  before it runs) or `r3` (a human consents to it). A rule only raises a
  tier: it never allows an operation the stock rules refuse, and where
  several rules match, the strictest applies.
- `consent_assurance`: required for `r3` and refused for `r2`. The weakest
  approver authentication the consent accepts: `device_trusted` (a declared
  local-operator posture, such as the operator of a stdio connection) or
  `person_authenticated`. A person satisfies either; a delegated service
  credential satisfies neither.
- `[governance.review.reviewer]`: the explicit model that reviews R2
  operations. There is no default model; without it an R2 operation is
  refused, never run at R1.

A reviewed MCP or tool-bundle operation shows its reviewer and consenting
human the account it acts with, as its own owner states it: the MCP
server's connector binding, its `oauth_account`, or its host's
`account = "none"` declaration (see
[the account an operation acts with](/api/mcp#the-account-an-operation-acts-with)),
or the account a host declared when it registered the bundle. An operation
whose owner states none is refused, never reviewed without it.

The stock host reads the rules from the realm's effective configuration when
the realm opens; a section that cannot be read or is malformed refuses the
realm's governed work. Unknown or misspelled fields are refused, including
inside the reviewer's identity.

Governance is administered by the realm's trusted host in the realm's own
config document. An ordinary config write (`config/set`, `config/patch`,
`PUT`/`PATCH /config`, the MCP config tool or the CLI) cannot change,
remove or restate the section, including a full replace that omits it, and
is refused with `governance_administration_required`. The section stays
readable through the ordinary config reads.

## OS process confinement

`[confinement]` selects the OS process confinement a stock host (`rkat`,
`rkat-rpc`, `rkat-rest` and `rkat-mcp`) applies to the processes its agents
launch: shell tool calls, background jobs and monitors (`shell`), command
hooks (`command_hooks`) and local MCP stdio servers (`mcp_stdio`). Without
the section, every launch runs as the trusted host, as before.

```toml
# Every launch kind: the workspace preset.
[confinement.all]
mode = "workspace"
network = "denied"           # the default; or "unrestricted"
read = ["/opt/toolchain"]    # extra read-only subtrees
write = ["/tmp/build"]       # extra writable subtrees

# A kind's own table replaces `all` for that kind in this document.
[confinement.mcp_stdio]
mode = "custom"
working_directory = "/srv/mcp"
requirement = { baseline = "command_runtime_v1", read = { kind = "paths", paths = [{ kind = "subtree", path = "/srv/mcp" }] }, write = { kind = "paths", paths = [] }, deny_read = [], deny_write = [], network = { kind = "denied" }, unix_connect = [], require_descendant_termination = false }
```

- `trusted_host`: no OS confinement, the default.
- `workspace`: the launched process reads and writes the host's workspace
  root and the `write` subtrees, reads the `read` subtrees, gets the
  `command_runtime_v1` platform baseline, and opens IP sockets only with
  `network = "unrestricted"`. The workspace root is the CLI's project root
  and a server's `--context-root`; a server started without `--context-root`
  refuses to start with this mode instead of confining nothing. Command hooks
  and MCP stdio servers start in the workspace root; the shell keeps its own
  working directory.
- `custom`: an explicit requirement in the confinement wire shape (see
  [native governed embedding](/rust/native-authorization)), and the absolute
  working directory of the command hooks and MCP stdio servers it confines.

Every path is absolute, without `.` or `..` components. Unknown keys, modes
and fields are refused, not ignored.

A launch the platform's backend cannot confine as required is refused at that
launch with typed `confinement_refused` feedback; it never runs unconfined,
and the rest of the run continues. At startup a host reports each launch
kind's requested and effective confinement (the backend that enforces it, or
that every launch of the kind is refused), what keeps the host's own inputs
from its confined processes, and each convention source it does not trust.
macOS uses Seatbelt. Linux uses namespaces and seccomp: it needs unprivileged
user namespaces, and it refuses deny lists, Unix socket grants, nested grants,
and granted paths that do not exist or pass through a symbolic link. Other
platforms refuse every confined launch. A confined process finds its program,
libraries and data only inside its granted subtrees and the platform
baseline; grant anything else it needs with `read`. A confined command hook
or MCP stdio server names its program by absolute path and receives only its
configured environment, never the host's; a relative program name or a loader
variable such as `LD_PRELOAD` refuses that launch.

### Composition

A requirement only ever holds or is added across the documents a realm
composes, from the most trusted: the user document (`~/.rkat/config.toml`,
which applies even when no document declares `[realm.global]`), then the
realm chain from its root to the head. A document's statement for a launch
kind is its own kind table, else its own `all`.

- The most trusted document that requires confinement for a kind decides it.
- A less trusted document may restate that requirement exactly or state
  nothing for the kind. Any other statement, `trusted_host` included, refuses
  the composition with an error naming both realms.
- A less trusted document can still add confinement for a kind that no more
  trusted document confines.

### The host's own inputs

A host that confines every launch kind keeps the inputs it reads its own
administration from out of its confined processes' reach:

- The realm state (every realm config document and the head realm's stores
  under the state root) and the user config document. A start in which a
  confined process could change one, by writing it, creating it where it is
  missing, or replacing a directory on the way to it, is refused, naming the
  input and the launch kind. Keep the state root and the user config root
  outside every write grant (`--state-root`, `--user-config-root`).
- The convention sources: the project and user `mcp.toml` files and the
  hooks of the project `.rkat/config.toml`. A source a confined process can
  write is not trusted. Each of its MCP servers is refused with
  `untrusted_configuration_source` before it is expanded, authorized,
  connected or spawned, and each of its hooks keeps its place and is refused
  at every invocation, so a mandatory guardrail withholds what it gates. A
  definition that a trusted source states identically is used from that
  source.

Each launch kind is judged on its own grants and protections: one kind's
protection does not cover another kind that writes the same place. On macOS
the `workspace` preset protects `<root>/.rkat` (the CLI's default realm state
and the project's convention files). The Linux backend has no deny lists, so
there the host's realm state must live outside the workspace.

A host that runs any launch kind as the trusted host claims none of this: its
startup report says that a process the agent drives can still change the
host's own inputs. `--confinement trusted-host` turns confinement off for the
whole process, with no such guarantee.

### Administration

Like [governance](#governance-settings), the section is administered by the
host in the document itself. An ordinary config write (`config/set`,
`config/patch`, `PUT`/`PATCH /config`, the MCP config tool or the CLI) cannot
add, change or remove it, including a full replace that omits it, and is
refused with `confinement_administration_required`. Restating it unchanged is
allowed. The section stays readable through the ordinary config reads.

### Operator flags

Each stock binary accepts `--confinement <trusted-host|workspace>`, with
`--confinement-network <denied|unrestricted>` and the repeatable
`--confinement-read <path>` and `--confinement-write <path>` for the workspace
preset. The flags replace the composed section for every launch kind of that
process, after composition: `--confinement trusted-host` is the operator's
explicit opt-out. They are never persisted, and no session, turn or API
parameter can carry them. Relative flag paths resolve against the working
directory.
